# Deployment guide

## Supported baseline

The verified application targets Node.js 22.12+ with a persistent writable filesystem, SQLite, and a single host. Run it under a process supervisor behind an HTTPS reverse proxy. A static export cannot provide authentication, server search, inquiries, or administration. Ephemeral serverless filesystems cannot safely retain SQLite or uploaded media.

No deployment or GitHub push has been performed by this implementation. These are operator instructions, not a claim of an existing production environment.

## Render deployment for this Next.js application

PythonAnywhere cannot run the Node.js server required by this app. Use a Render Node web service with a paid persistent disk instead. The checked-in `render.yaml` supplies a single instance, a 1 GB disk mounted at `/var/data`, generated session secret, and manual deploys. Review current service and disk charges before creating it; no hosting account or paid service has been provisioned here.

1. Create a Render account at <https://dashboard.render.com/register> and connect the GitHub account with access to `anabel-codes/ISQA8210-TermProject`.
2. After the application is merged, choose **New > Blueprint**, select this repository, and use branch **main** with `render.yaml`.
3. Set `NEXTAUTH_URL` to the exact HTTPS origin assigned to the service (for example `https://isqa8210-termproject.onrender.com`; check the actual assigned name). Review the paid compute and disk choices before creating resources. If the final URL differs, update the variable and redeploy.
4. The build script installs development dependencies and builds against a disposable migrated database. Render does not mount the persistent disk during build or pre-deploy. The start script applies migrations to `file:/var/data/site.db` at runtime, then listens on Render's `PORT` on `0.0.0.0`. Media is stored at `/var/data/media`. No inventory or users are seeded automatically.
5. Open the service **Shell**. For an academic demo only, run `npm run db:seed` to add clearly labeled fictional inventory. To create the first administrator without displaying or saving its password in command history:

   ```bash
   read -rp 'Admin email: ' ADMIN_EMAIL
   read -rsp 'New admin password: ' ADMIN_PASSWORD; echo
   export ADMIN_EMAIL ADMIN_PASSWORD
   npm run admin:create
   unset ADMIN_EMAIL ADMIN_PASSWORD
   ```

6. Visit the public HTTPS URL and `/login`. Run the acceptance checks above, including an inquiry, listing upload, and restart persistence. Keep the service to one instance and take consistent SQLite backups plus media backups before future migrations. Rollbacks require checking database compatibility; reverting code does not undo migrations.
7. Automatic deploys are disabled so new commits do not change the public demo unexpectedly. Deploy the reviewed main commit manually after CI passes. Arrange daily analytics pruning in the same service runtime; a separate Render cron service cannot mount this service's disk. Until scheduling is configured, run `npm run analytics:prune` from the service Shell daily.

Keep `TRUST_PROXY=false` unless the proxy's forwarded-IP behavior has been verified. The build and start scripts do not use the local development database or copy local secrets. Their migration commands explicitly set `RUST_LOG=info` to avoid the SQLite engine initialization failure reproduced when the host inherits `RUST_LOG=warn` (Prisma issue #29355).

References: [Render Next.js](https://render.com/docs/deploy-nextjs-app), [persistent disk limits](https://render.com/docs/disks), [Blueprint fields](https://render.com/docs/blueprint-spec), [PythonAnywhere staff on Node hosting](https://www.pythonanywhere.com/forums/topic/33573/).

## Build and start on a persistent Node host

1. Provision the repository and Node 22.12+. Install dependencies with `npm ci` (include build/dev dependencies during build).
2. Supply production environment securely. Do not upload development `.env` or its credentials.
3. Set a strong `NEXTAUTH_SECRET` generated by `openssl rand -base64 48` and canonical `NEXTAUTH_URL=https://your-domain.example`.
4. Set an absolute database URL, for example `DATABASE_URL=file:/srv/carlos/data/site.db`, and writable `MEDIA_ROOT=/srv/carlos/media`. The application process needs access only to its directories.
5. Run `npm run db:migrate`, then `npm run build`. The database must be reachable because pages/layouts read settings.
6. Initialize the first administrator using temporary `ADMIN_EMAIL` and `ADMIN_PASSWORD` values and `npm run admin:create`. Remove initialization credentials afterward.
7. Run `npm start -- --hostname 127.0.0.1 --port 3000` under the supervisor; proxy HTTPS requests to it. The origin must match `NEXTAUTH_URL` exactly.
8. Open the public pages, sign in, upload a photograph, create a draft, publish/unpublish it, and submit/review a test inquiry. Verify the media directory survives restarts.
9. Confirm the sample banner and labels suit the intended environment. Do not silently present sample inventory as real. Seed only a demonstration environment; real production inventory requires verified authorized data.

The reverse proxy should cap request bodies at 9 MB, set security/TLS policy, and overwrite forwarded client-IP headers. Set `TRUST_PROXY=true` only when that overwrite is guaranteed. Otherwise leave it false: public throttles intentionally share one local bucket. Never trust arbitrary client-supplied forwarded headers. The login additionally limits per-account and global attempts; this can produce a shared lockout under heavy abuse and may require an edge limiter for production.

Schedule `npm run analytics:prune` daily with the same database environment. It removes observations older than 90 days and expired rate buckets. Establish a separate inquiry retention/deletion policy with the operator; the application intentionally does not silently delete contact records.

## Persistent storage and backups

Back up both the database and media. Use SQLite's online backup API or the SQLite CLI `.backup` command for a consistent live snapshot rather than copying an active file without coordination. Restrict backup access, encrypt backups as appropriate, define a retention policy and test restores. Do not place the database under `public` or serve it through the reverse proxy.

Media is re-encoded to WebP, capped at 2000 pixels wide, and given a random filename. The `/uploads/[file]` route reads only filenames matching that format. Removed/replaced photographs are detached from records but retained on disk. Automatic orphan garbage collection is not implemented. An operator can reconcile referenced `PropertyImage.url` values before deleting unreferenced files after a recovery period.

## PostgreSQL conversion (documented path, not verified deployment)

For multiple application hosts, migrate the database and media together. A PostgreSQL URL alone does not switch the checked-in SQLite adapter.

1. Back up existing data. Create a conversion branch and a new empty PostgreSQL database.
2. Install matching Prisma adapters: `npm install @prisma/adapter-pg@7.10.1 pg` and `npm install -D @types/pg`. Keep Prisma CLI/client/adapter versions aligned.
3. Change `datasource db` in `prisma/schema.prisma` to `provider = "postgresql"`. Keep `prisma.config.ts` reading `DATABASE_URL`; set it to the PostgreSQL connection URL in the deployment environment.
4. Replace the SQLite adapter in `src/lib/db.ts`:

```ts
import { PrismaClient } from '@prisma/client';
import { PrismaPg } from '@prisma/adapter-pg';

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
const prisma = new PrismaClient({ adapter });
```

Preserve the existing development singleton/export pattern. Use trusted TLS certificates and provider-recommended connection pooling.

5. Archive the SQLite migration history outside the active PostgreSQL migration directory in this conversion branch. Generate a fresh initial PostgreSQL migration with `npx prisma migrate dev --name initial_postgresql` against a disposable development PostgreSQL instance. Do not apply SQLite SQL to PostgreSQL. Keep the SQLite history in Git history/documented archives.
6. Export and validate source records, including timestamps/IDs, integer cents, and FK relationships. Import User and Property before dependent images/features/inquiries/events. Reconcile counts and orphan checks. A tested import utility is future work; do not manually improvise on a live database.
7. Adapt database-backed tests to a temporary isolated PostgreSQL database/schema and rerun all authorization, publication, inquiry and browser workflows. Confirm case-insensitive location behavior deliberately; PostgreSQL contains matching differs from SQLite. Add `mode: 'insensitive'` where appropriate after generating the PostgreSQL client.
8. Deploy migrations with `npm run db:migrate`, regenerate the client, build, and run acceptance checks before switching traffic. Retain the prior database and restore plan until cutover is accepted.

No live PostgreSQL account or migration was configured in this task.

## Shared/object media

Multiple nodes need shared persistent media or an object-storage adapter. Replace the upload writer and media resolver together; store only approved asset keys/URLs and update the Zod image URL allowlist and Next image policy. Validate object size/type, re-encode before storage, limit access, and keep storage credentials server-only. Existing code uses local media and does not claim an S3/R2 integration.

## Operational security and limitations

Use HTTPS, random secrets, separate environments and restricted database/media permissions. Do not expose port 3000 directly when relying on proxy headers. NextAuth uses secure cookies when configured for HTTPS. Password resets/account deactivation revoke sessions at the next authorization check. There is no MFA, public account registration, self-service recovery, or granular administrator permission model.

The included CSP allows inline styles/scripts for Next.js; strict per-request nonces would require further work. No HSTS header is forced in local development; configure it at the HTTPS edge after confirming domain readiness. Do not log inquiry bodies or passwords. Review administrative access and backup protections before collecting real customer data.

Email notifications, feed ingestion, monitoring integrations and automated inquiry deletion are not implemented. Persisted inquiries remain available in the dashboard without email. Database migrations and CI configuration must be reviewed through the team's PR process before production rollout.
